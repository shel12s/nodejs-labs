## 2. Використані технології

### Node.js
Однопотокове середовище виконання JS на сервері. Завдяки **Event Loop** Node.js обробляє I/O-операції (запити до БД, мережа) неблокуючим способом: поки очікує відповідь від MySQL, він обробляє інші запити. Це робить сервер ефективним навіть при великій кількості одночасних з'єднань без потреби у потоках (threads).

### Promises та async/await
Promises — об'єкти, що представляють результат асинхронної операції (pending → fulfilled/rejected). `async/await` — синтаксичний цукор над Promises, що дозволяє писати асинхронний код у лінійному стилі без "callback hell".

Ключова оптимізація — **`Promise.all()`**: запускає кілька незалежних промісів **паралельно**, замість послідовного виконання. Це безпосередньо пов'язано з Event Loop — обидва запити до БД потрапляють у чергу подій одночасно, не блокуючи один одного.

```js
// Послідовно (оригінал) — сумарний час: ~t1 + t2
const user     = await userService.getUserById(id);   // чекаємо...
const contacts = await contactService.getContacts(id); // тільки потім

// Паралельно (нова версія) — сумарний час: ~max(t1, t2)
const [user, contacts] = await Promise.all([
    userService.getUserById(id),
    contactService.getContacts(id)
]);
```

### MySQL + mysql2/promise
`mysql2/promise` надає нативну підтримку Promises для пулу з'єднань MySQL. Пул (`createPool`) автоматично управляє кількома з'єднаннями, що дозволяє обслуговувати паралельні запити без очікування звільнення одного з'єднання. Запити виконуються через параметризовані placeholders (`?`), що захищає від SQL-ін'єкцій.

## 4. Обґрунтування рішень

### Чому `bcrypt.compare()` є обов'язковим
`bcrypt.hash()` — **однобічна** функція: відновити оригінальний пароль з хешу неможливо. Тому єдиний спосіб перевірки — `bcrypt.compare(plaintext, hash)`, яка внутрішньо хешує введений пароль і порівнює результати. Пряме порівняння рядків (`===`) — це груба помилка безпеки.

### Чому важливий порядок маршрутів в Express
Express перевіряє маршрути **зверху вниз** у порядку реєстрації. Параметричний маршрут `/:id` — жадібний: він збігається з будь-яким рядком, включно з `"edit"` і `"delete"`. Якщо `/:id` зареєстровано першим, запит `GET /users/edit/5` обробляється як `id = "edit"`, а не як маршрут редагування. Специфічні маршрути **завжди** мають бути вище параметричних.

### Чому `Promise.all()` пришвидшує роботу
Event Loop Node.js — однопотоковий, але I/O (запити до БД) виконується **асинхронно**. При послідовному `await` другий запит починається тільки після завершення першого. `Promise.all()` передає обидва запити до черги подій **одночасно**: MySQL обробляє їх паралельно, і загальний час очікування дорівнює часу найповільнішого запиту, а не їх сумі.

### Чому глобальний error handler необхідний
У Express 4+ помилки, кинуті в `async`-функціях (без явного `next(err)`), не передаються до глобального обробника автоматично — сервер зависає без відповіді клієнту. Глобальний `(err, req, res, next)` обробник забезпечує єдину точку обробки всіх непередбачених помилок і коректну відповідь 500.

### Чому видалено `db/database.js`
Файл підключав іншу базу даних (`user_demo`) і ніде не імпортувався. Мертвий код збільшує когнітивне навантаження при читанні проєкту та може ввести в оману — наприклад, призвести до використання неправильного підключення при рефакторингу.
